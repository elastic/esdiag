## Why

ESDiag configures four kinds of external systems through four unrelated command shapes:
- `esdiag setup [HOST]` (Elasticsearch or Kibana assets, chosen by the saved host's `app`, or both from environment variables when `HOST` is omitted)
- `esdiag agent skills` (coding-agent harnesses)
- `esdiag completions install <shell>` (shell configuration, unreleased in #430)
- `esdiag local up` (container runtime)

Users have to know which noun each action hides behind. `agent` mixes a runtime action (`ask`) with an installer (`skills`). Bare `esdiag setup` quietly changes meaning depending on which `ESDIAG_*` variables happen to be set. Every combined setup path (bare `esdiag setup`, `esdiag init`, web onboarding, `esdiag local`) also starts an Elasticsearch trial license whenever Agent Builder licensing is inactive. That means re-running setup during an upgrade can start a trial on a production or working cluster.

Issue #431 consolidates every "configure an external system for ESDiag" action under one verb, `setup`, with the external system or configuration source as an explicit subcommand. The code is organized the same way: one module under `src/setup/` per target, with bundled content under `assets/`.

## What Changes

- **BREAKING** Replace `esdiag setup [HOST]` with explicit subcommands. Running `esdiag setup` with no subcommand prints help and exits non-zero.
  - `esdiag setup elasticsearch [HOST]` installs Elasticsearch assets into a saved Elasticsearch host, or into the persisted default output when `HOST` is omitted.
  - `esdiag setup kibana [HOST]` installs Kibana assets into a saved Kibana host, or into the persisted default output's linked viewer when `HOST` is omitted.
  - `esdiag setup output [NAME] [--activate-trial]` installs Elasticsearch and Kibana assets into a saved output deployment: the named Elasticsearch `send` host and its linked Kibana viewer, or the persisted default output when `NAME` is omitted. It replaces bare `esdiag setup` without environment variables.
  - `esdiag setup env [--env-file <PATH>] [--activate-trial]` installs assets into the Elasticsearch and/or Kibana declared by `ESDIAG_OUTPUT_*`, `ESDIAG_KIBANA_URL`, and `ESDIAG_KIBANA_SPACE`, read from the process environment and, optionally, from a `.env` file. It sets up whichever services are declared.
  - `esdiag setup context [NAME] [--config <PATH>] [--activate-trial]` installs assets into whichever Elasticsearch and/or Kibana services an Elastic CLI `.elasticrc` context defines (the current context when `NAME` is omitted). Credentials resolve through the `elasticrc` workspace crate and are never copied into `hosts.yml` or the keystore.
- **BREAKING** Starting an Elasticsearch trial license becomes opt-in for every manual setup path, because a cluster that isn't the local stack is assumed to be licensed already. Only `setup output`, `setup env`, and `setup context` can start one. They do so only when they install both Elasticsearch and Kibana assets, licensing is inactive, and the caller passes `--activate-trial` or sets `ESDIAG_SETUP_ACTIVATE_TRIAL=true`. Without opt-in, an inactive license means Elasticsearch assets install, the Enterprise-dependent Kibana stage is skipped, and the outcome is `partial` with a warning naming both opt-ins. Re-running setup never changes the cluster license unless asked.
- The local stack keeps activating a trial on first run, because it is often the first place someone tries the Agent Builder features. `esdiag local` and `esdiag-local` gain `--activate-trial=true|false` and honor `ESDIAG_SETUP_ACTIVATE_TRIAL`, at parity, on `up`, `setup`, and `upgrade`. When neither is given, they read `GET _license/trial_status` and activate only when the local cluster has never had a trial. That covers a new stack, including a retried first `up`, and never a later re-run. The resolved value is passed to the setup run and is not persisted.
- `esdiag init` (for an existing output) and web onboarding ask separately, defaulting to no, before starting a trial. Declining keeps the rest of onboarding valid. `esdiag init` starting a new local stack relies on the local default and asks nothing.
- **BREAKING** Replace `esdiag agent skills [--target <AGENT>]... [--force]` with `esdiag setup skills [AGENT]... [--force]`. `esdiag agent` keeps `ask`.
- **BREAKING (unreleased only)** Replace #430's `esdiag completions <SHELL>` and `esdiag completions install <SHELL>` with `esdiag setup completions <SHELL> [--print]`. Extracting the embedded completion script is in `setup` scope.
- No compatibility aliases. ESDiag is pre-1.0, and the old forms are removed in the same release.
- Update the compose definitions generated by `bin/esdiag-local` and `src/local.rs`, plus the native core-mode invocation in `bin/esdiag-local`, to run `setup env`. The generated command is chosen from the state's pinned ESDiag image version, so stacks pinned to an older image keep running `setup`.
- `esdiag local …` and `esdiag-local …` keep their current commands and parity, including `local setup`. Only the ESDiag command they run internally changes.
- Reorganize `src/setup.rs` (85 KB) into `src/setup/{mod,install,pipeline,license,elasticsearch,kibana,env,context,skills,completions}.rs`. Move `src/completions.rs` and `src/agent/skills.rs` under it, and keep `esdiag::setup::{assets, assets_report, asset_statuses, assets_installed, SetupReport}` as stable library paths. `ensure_agent_builder_license` is replaced by `agent_builder_license_status` (read-only) and `activate_trial_license` (explicit).

## Capabilities

### New Capabilities

- `cli-setup-command`: The `esdiag setup` command family. It covers target subcommands, saved output, environment and `.env`, and `.elasticrc` context setup, partial-deployment handling, opt-in trial activation, and feature gating.

### Modified Capabilities

- `cli-agent-skills`: The installer command moves to `esdiag setup skills`, with targets as positional arguments, and onboarding recovery guidance names the new command.
- `cli-structured-output`: The raw completion script stream moves to `esdiag setup completions <SHELL> --print`, and installation emits `completion_installed` from `esdiag setup completions <SHELL>`.
- `standalone-local-stack`: The full-mode one-shot setup container runs `esdiag setup env`, with a version-aware fallback for stacks pinned to an older image, and a trial is activated by default only on a cluster that has never had one, overridable with `--activate-trial` / `ESDIAG_SETUP_ACTIVATE_TRIAL`.
- `embedded-local-stack-launcher`: `esdiag local` applies the same trial default and override at parity with `esdiag-local`.
- `cli-first-run-onboarding`: `esdiag init` asks separately, defaulting to no, before starting a trial on an existing output. It asks nothing for a new local core stack.
- `gui-onboarding`: The web asset-setup stage requires an explicit, unchecked-by-default trial choice.

## Impact

- **Target Elastic product:** Elasticsearch and Kibana (asset installation, unchanged asset content). The change also touches the Elastic CLI `.elasticrc` configuration format (read-only) through the existing `crates/elasticrc` crate.
- **CLI:** Affected. The command tree, help, generated completion scripts, and onboarding guidance all change. Outcome kinds (`setup_completed`, `agent_skills`, `completion_installed`) and the failure category `setup_failed` stay the same.
- **Web UI / desktop:** The web onboarding asset-install step (`src/server/web_onboarding.rs`, `templates/welcome.html`) gains an unchecked "Start an Elasticsearch trial license" choice. Other server paths call the setup library in process and do not change. Offline docs embedded through `DocsAssets` pick up the updated `docs/` pages.
- **Core processing:** No change.
- **Containers and launchers:** Generated compose files, `bin/esdiag-local` core mode, `docker run … setup` documentation, and their shell tests change to `setup env`.
- **Packaging:** The main crate gains a path dependency on `elasticrc` and a `.env` parser dependency behind the `setup` feature. The `elasticrc` GitHub workflow runs because it watches `Cargo.toml`/`Cargo.lock`.
- **Agent assets:** The canonical skill in `.agents/skills/esdiag/` and its generated `plugin/skills/esdiag/` copy change command text, which changes the embedded skill digest.
